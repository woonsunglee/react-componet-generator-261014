# TDD Rule

**WARNING: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**

## 우선순위

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 해당 규칙을 우선 적용한다. 이 파일은 프로젝트별 규칙이 없을 때의 **기본값(fallback)** 이다.

---

## 적용 기준

### TDD 필수 적용 대상

- 비즈니스 로직 (도메인 규칙, 계산, 검증)
- API 핸들러 및 엔드포인트
- 유틸리티 함수 (순수 함수)
- 버그 수정 (재현 테스트 먼저 작성)
- 상태 관리 로직 (reducer, store)
- 데이터 변환/파싱 함수

### TDD 불필요 대상

- 타입 정의 (interface, type alias)
- 설정 파일 (config, env)
- 순수 UI 컴포넌트 (스타일만 있는 presentational component)
- SQL/쿼리문 (별도 통합 테스트로 검증)
- 외부 라이브러리 래퍼 (단순 위임)

---

## RED-GREEN-REFACTOR 사이클

### 1. RED (실패하는 테스트 작성)

- **하나의 동작 = 하나의 테스트**. 여러 동작을 한 테스트에 넣지 마라.
- 테스트 작성 후 **반드시 실행하여 실패를 확인**하라.
- 실패 이유는 **"기능 미구현"** 이어야 한다.
  - 문법 오류, import 누락, 타입 에러로 실패하면 테스트 자체가 잘못된 것이다.
- 실패 메시지가 무엇을 구현해야 하는지 명확히 알려주도록 작성하라.

### 2. GREEN (테스트 통과시키기)

- **최소한의 코드만 작성**하라. 동작하게 만드는 것이 목표다.
- **YAGNI 원칙**: 테스트가 요구하지 않는 기능은 추가하지 마라.
- 하드코딩도 허용된다. 리팩터링 단계에서 일반화하라.
- **신규 테스트 + 기존 테스트 모두 통과**해야 GREEN이다.
- 기존 테스트가 깨지면 GREEN이 아니다. 수정하라.

### 3. REFACTOR (코드 개선)

- 중복 제거, 이름 개선, 헬퍼 함수 추출을 수행한다.
- **GREEN 상태를 유지**하라. 리팩터링 중 테스트가 깨지면 즉시 롤백하라.
- **새로운 동작을 추가하지 마라**. 새 동작은 새 RED 사이클에서 다룬다.
- 리팩터링 후 반드시 테스트를 실행하라.

### 4. REPEAT (반복)

- 다음 동작에 대한 **RED 단계로 돌아간다**.
- 모든 요구사항이 테스트로 표현될 때까지 반복한다.

---

## 삭제 강제 규칙

**테스트 전에 프로덕션 코드를 먼저 작성했다면:**

1. 해당 프로덕션 코드를 **삭제**한다.
2. RED 단계부터 다시 시작한다.
3. **"참고용으로 남겨두겠다"는 변명은 허용되지 않는다.**

이유: 테스트 없이 작성된 코드는 테스트가 설계를 주도하지 못했다. TDD의 핵심 가치인 "테스트가 API를 결정한다"가 무너진다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트도 단순하다. 작성 시간 10초. 미래의 회귀 방지 가치는 무한. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 지금 작성하지 않으면 영원히 작성되지 않는다. |
| "시간이 없다" | 버그 수정 시간 > 테스트 작성 시간. TDD는 시간을 절약한다. |
| "삭제하면 낭비" | 잘못된 방향으로 간 코드를 유지하는 것이 진짜 낭비다. |
| "프로토타입이다" | 프로토타입 코드가 프로덕션에 들어가는 것을 수백 번 봤다. 처음부터 제대로 하라. |
| "이건 테스트하기 어렵다" | 테스트하기 어려운 코드는 설계가 잘못된 것이다. 설계를 바꿔라. |

---

## 체크리스트

코드 리뷰 또는 self-review 시 확인:

- [ ] 모든 비즈니스 로직에 테스트가 있는가?
- [ ] 테스트가 프로덕션 코드보다 먼저 작성되었는가?
- [ ] 각 테스트는 하나의 동작만 검증하는가?
- [ ] 테스트 실패 메시지가 문제를 명확히 설명하는가?
- [ ] 불필요한 코드(테스트가 요구하지 않는 코드)가 없는가?
